## 0. 이 문서에 대하여

프로젝트의 **개발 환경 표준**을 정의한다. 폴더 구조, 네임스페이스, 코드 컨벤션, 패키지 등 직군 무관 협업 규칙이 아닌 **플밍 파트 내부 약속**을 다룬다.

빠른 개발이 목표이므로, 구조는 가볍게 시작하고 필요할 때 확장한다. 처음부터 과한 폴더 트리나 추상화를 깔지 않는다.

> **개발 환경은 미션 가이드로 확정되었다.** 협약사(유닉온)가 "실무와 동일한 환경 체험"을 위해 지정한 환경을 그대로 따른다. 임의로 버전·도구를 바꾸지 않는다.

## 2. 폴더 구조

「총알소녀」 기준 골격이다. 기능 폴더는 필요할 때 추가한다.

```
Docs/                       # 문서 (가이드, 작업 노트 등)
Assets/
├─ Imports/                 # 외부·유료 에셋 (gitignore 대상)
├─ Project/                 # 핵심 폴더
│  ├─ Art/                  # 직접 제작 또는 외부 에셋 수정본
│  │  ├─ Animations/
│  │  ├─ Audio/
│  │  └─ Sprites/           #   기물·슬롯·포탑·몬스터·이펙트
│  ├─ Data/                 # 데이터 드리븐 파일
│  │  ├─ Json/              #   런타임 로드용 JSON
│  │  └─ Source/            #   Excel/CSV 중간 편집본
│  ├─ Prefabs/              #   기물·슬롯·포탑·몬스터, 로거 UI 캔버스 등
│  ├─ Resources/            # 런타임 동적 로드 대상
│  ├─ Scenes/               # Lobby / InGame / Result
│  └─ Scripts/
│     ├─ Core/              # 코어 레이어 (코어 문서 참고)
│     │  ├─ Managers/       #   각종 매니저
│     │  ├─ Singletons/     #   Singleton.cs (SingletonBase + Singleton<T>)
│     │  └─ (직하)          #   Logger.cs, Define.cs 등
│     ├─ InGame/            # 인게임 시스템
│     │  ├─ Sort/           #   3-Sort 슬롯·기물·정렬 판정
│     │  ├─ Defense/        #   포탑·몬스터·웨이브·전투
│     │  └─ Growth/         #   경험치·레벨업·특전(강화)·콤보
│     ├─ Lobby/             # 스테이지 선택, 로비 흐름
│     ├─ UI/                # 공용 UI
│     └─ Utils/             # 범용 유틸리티 (코어와 분리)
├─ Settings/                # Unity 세팅
└─ WIP/                     # 정리 전 개인 작업 공간 (자유)
```

규칙:

- 개인 실험·테스트 작업은 `WIP/`에서 한다. 공유 단계에서 `Project/` 적절한 위치로 옮긴다.
- 외부 에셋은 `.gitignore` 대상인 `Imports/`에 둔다. 외부 에셋을 **수정해서 공유**해야 하면 `Art/`로 옮겨 관리한다.
- 에디터 전용 스크립트는 `Editor` 폴더에 둔다 (빌드에서 제외됨).
- 데이터 파일은 `Project/Data/`에 둔다. 자세한 규칙은 [6장](#6-데이터-드리븐-작업-규칙).

## 3. 네임스페이스

- 코어 코드는 `Core` 네임스페이스를 쓴다.
- 그 외에는 **기능 단위 네임스페이스**를 쓴다. 폴더 이름에 맞추어 간단하게 짓는다.
- 하위 구분이 필요하면 `루트.상위.하위` 형태를 쓴다.

| 네임스페이스 | 용도 |
|---|---|
| `Core` | 싱글톤, 매니저, Define, DataManager, Logger 등 코어 레이어 |
| `InGame.Sort` | 3-Sort 슬롯·기물·정렬 판정 |
| `InGame.Defense` | 포탑·몬스터·웨이브·전투 |
| `InGame.Growth` | 경험치·레벨업·특전(강화)·콤보·필살기 |
| `Lobby` | 스테이지 선택, 로비 흐름 |
| `UI` | 공용 UI 컴포넌트 |
| `Utils` | 범용 유틸리티 (특정 게임 시스템에 속하지 않는 도구) |

> 폴더 구조와 네임스페이스를 맞춰 둔다. 시스템이 늘면 하위 네임스페이스를 추가한다.

## 4. 코드 컨벤션

### 4.1 네이밍

```csharp
// 클래스 / 구조체 / 열거형: PascalCase
public class MonsterSpawner { }

// 메서드: PascalCase
void SpawnMonster() { }

// 변수 / 매개변수: camelCase
float spawnInterval;

// private 필드: _camelCase
private int _currentWave;

// 상수: UPPER_CASE
const int MAX_SLOT = 7;

// 프로퍼티: PascalCase
public bool IsCleared { get; private set; }

// 인터페이스: I 접두사
public interface IDamageable { }

// 추상 클래스: Base 접미사
public abstract class SkillBase { }
```

### 4.2 주석

WHAT(무엇)이 아니라 **WHY(왜)**를 적는다. 코드만 봐도 아는 것은 주석으로 반복하지 않는다.

```csharp
// ✅ 좋은 주석 — WHY
// 같은 종류 3개가 모이면 정렬 완료 — 콤보 판정을 위해 직전 완료 시각 기록
_lastSortTime = Time.time;

// ❌ 나쁜 주석 — WHAT만 반복
// 시간 저장
_lastSortTime = Time.time;
```

- 네이밍을 명확히 하여 과한 주석을 피하고 가독성을 높인다.
- 핵심 로직·설명이 필요한 부분만 주석을 단다.

### 4.3 설계 권장

- **폴링보다 이벤트**: 매 프레임 상태를 물어보는 대신, 상태 변경 시점에 이벤트를 발행하는 구조를 권장한다. (`Update` 부하·결합도 감소.)
- 이벤트를 구독하면 **반드시 해제**한다. 종료 시 해제는 코어 문서의 `IsQuitting` 가드를 참고한다.
- 게임플레이 수치는 코드에 하드코딩하지 않고 데이터 시트로 뺀다. ([6장](#6-데이터-드리븐-작업-규칙).)
- 코드 구조 관련 매직 넘버·매직 스트링은 `Core.Define`으로 모은다.
- **인터페이스 계약 우선**: 시스템 간 연결은 인터페이스 시그니처를 먼저 합의한 뒤 양쪽이 병렬로 개발한다. 인터페이스 변경은 팀에 공유한다. 플밍 4인이 병렬로 일하려면 이 합의가 특히 중요하다.

### 4.4 모바일 성능 주의

- 매 프레임 `string.Format` 등으로 텍스트를 갱신하면 GC가 쌓여 프레임 스파이크가 생긴다. 텍스트 갱신은 일정 주기(예: 0.5초)로 제한한다. 단, 시각적으로 부드러워야 하는 값(게이지 `fillAmount` 등)은 매 프레임 갱신하도록 분리한다.
- 몬스터처럼 다수 생성·파괴되는 오브젝트는 **오브젝트 풀링**을 적용한다. 매 웨이브 `Instantiate`/`Destroy`를 반복하면 모바일에서 끊김이 생긴다.
- 저사양 안드로이드 기기를 기준으로 최적화한다. 실기기 테스트를 빌드 단계마다 한다.

## 5. 패키지 / 플러그인

### 5.1 추가 규칙

- 외부 플러그인·패키지는 사용 전 **라이선스 확인 + 팀장 승인**.
- 추가 후 반드시 소통 채널에 통보한다. (신규 셋업·빌드 영향.)
- 유료·외부 에셋은 `Imports/`에 두고 `.gitignore` 처리한다.
- `.gitignore`된 플러그인이 필요한 팀원은 팀장에게 패키지를 요청한다.
- 외부 리소스를 쓰면 **라이선스 문서·출처 링크를 보관**한다. (유닉온 산출물 요건.)

### 5.2 사용 패키지

| 분류 | 패키지 | 용도 | 상태 |

| 연출 | DoTween | UI·오브젝트 트윈 연출 | 미션 지정 — 필수 |

## 6. 데이터 드리븐 작업 규칙

미션 필수 기술이다. 코어 문서 7장(`DataManager`)과 함께 본다.

- 게임플레이 수치(스테이지 구성, 몬스터 스탯, 경험치 곡선, 스킬·선택지 풀, 인게임 텍스트 등)는 **코드가 아니라 데이터 파일**에 둔다.
- 데이터 원본은 Google Spreadsheet에서 기획이 관리한다. 개발은 이를 Excel/CSV로 받아 `Data/Source/`에 두고, JSON으로 변환해 `Data/Json/`에 둔다. 게임은 JSON을 읽는다.
- 데이터 테이블마다 **직렬화용 클래스(DTO)**를 1:1로 둔다. 시트 컬럼 구성(스키마)이 바뀌면 DTO도 함께 바꾸고 기획에 공유한다.
- 수치 조정만으로 끝나는 변경은 **코드 수정 없이** 시트 갱신 → JSON 재변환으로 끝나야 한다. 데이터 변경에 매번 코드를 고쳐야 한다면 구조가 잘못된 것이다.
- 최종 산출물에 **메타데이터가 정리된 JSON/Excel**이 포함된다. 데이터 파일은 처음부터 제출물이라는 전제로 정돈해 둔다.

## 7. 렌더링 방침 (월드 스페이스 / UGUI)

게임 요소를 월드 스페이스 SpriteRenderer로 둘지 UGUI 캔버스로 둘지를 미리 정한다. 「총알소녀」는 슬롯·기물·포탑·몬스터가 서로 충돌·공간 상호작용을 하므로 둘을 명확히 가른다.

**판단 기준**: 물리·충돌·공간 상호작용이 있으면 월드 스페이스, 화면에 고정된 정보·메뉴면 UGUI.

| 구분 | 대상 | 구현 |
|---|---|---|
| 게임플레이 | 슬롯, 기물, 포탑, 몬스터, 발사체, 인게임 이펙트 | 월드 스페이스 SpriteRenderer + `Collider2D` |
| 정보 UI | 체력·경험치 게이지, 웨이브 목표·시간, 일시정지·특전 팝업 | UGUI |
| 화면 UI | 로비, 스테이지 선택, 정산 페이지 | UGUI |

- 게임플레이 요소는 같은 `Sorting Layer` / `Order in Layer` 체계로 깊이를 정리한다.
- 기물 드래그 입력은 두 영역에 걸친다. `InputManager`가 스크린 좌표를 발행하고, 게임플레이 측이 `ScreenToWorldPoint`로 월드 좌표를 얻어 처리한다. (코어 문서 6.3 참고.)
- UI는 미션 지정 에셋 UGUI로 구현한다.

## 8. 씬 관리

씬은 로비 / 인게임 / 정산(Result) 정도로 단순하게 유지한다.

- 개인 테스트 씬은 `Test_이름` 형식으로 각자 `WIP/`에서 작업한다.
- **같은 씬을 두 명이 동시에 작업하지 않는다.** 필요하면 복사 후 병합하며, 병합은 프리팹·코드 단위로 진행한다.
- 씬 수정 시 사전 통보한다.
- 작업물은 프리팹화하여 제출한다.
- 메인 씬 관리 담당: (역할 분담 확정 후 기입)

## 9. 빌드 (Android)

최종 산출물이 안드로이드 APK이므로, 빌드는 막판이 아니라 각 단계마다 확인한다.

- **Build Target**: Android. 셋업 직후 빈 프로젝트로 APK 빌드가 한 번 통과하는지 확인한다.
- 단계별 빌드(데모/CBT/OBT/최종)마다 **실기기에서 APK를 직접 구동**해 본다. 에디터에서만 확인하면 터치 입력·성능·해상도 문제를 놓친다.
- 빌드 설정(패키지명, 아이콘, 해상도, 최소 API 레벨 등)은 확정되면 이 장에 표로 기록한다.
- 릴리즈 APK에는 디버그 UI가 노출되지 않는다. (`Logger`가 `Debug.isDebugBuild`로 자동 비활성 — 코어 문서 3.4.)

### 9.1 Player Settings — 화면 회전

세로 화면 컨셉에 맞춰 **세로 모드 고정**으로 설정한다.

| 방향 | 설정 |
|---|---|
| Portrait | 허용 |
| Portrait Upside Down | 허용 |
| Landscape Left | 차단 |
| Landscape Right | 차단 |

위치: `Edit > Project Settings > Player > Resolution and Presentation > Allowed Orientations for Auto Rotation`.

## 10. 개발 워크플로우

### 10.1 작업 시작 전

1. 최신 버전 Pull
2. 씬·데이터 변경 여부 확인
3. 작업 브랜치 생성 (`feat/기능명_작성자`)

### 10.2 작업 중

1. 자주 테스트한다.
2. 콘솔 에러는 즉시 해결한다. 에러를 안고 다음 작업으로 넘어가지 않는다.
3. 변경 의도가 드러나도록 주석·커밋 메시지를 작성한다.

### 10.3 작업 완료 후

1. 씬 저장 (`Ctrl+S`)
2. 테스트 플레이로 동작 확인
3. 커밋 + 푸시 (의미 있는 메시지)
4. PR 생성 및 팀원 공유

## 11. 긴급 상황 대처

### 씬이 깨졌을 때

1. 백업 씬으로 복구한다.
2. Git에서 이전 버전을 체크아웃한다. **메타파일(.meta) 포함.**
3. 해결이 안 되면 팀원에게 도움을 요청한다.

### 코드가 동작하지 않을 때

1. 콘솔 에러 메시지를 먼저 읽는다.
2. `Debug.Log` 또는 `Logger`로 변수 값을 출력해 확인한다.
3. 막히면 길게 끌지 말고 코드 리뷰를 요청한다.

### 데이터 로드가 깨졌을 때

1. JSON 파일과 DTO 클래스의 스키마가 일치하는지 확인한다.
2. `Logger`로 누락·중복 키 에러를 확인한다. (코어 문서 7.3.)
3. 시트 구조가 바뀐 것이면 기획과 스키마를 다시 맞춘다.
