## 0. 이 문서에 대하여

프로젝트의 **코어 레이어**(`Core` 네임스페이스)를 정의한다. 코어 레이어는 모든 매니저·시스템이 공통으로 깔고 시작하는 기반 코드다. 빠른 개발이 목표이므로, 매 프로젝트에서 검증된 동일한 코어 베이스를 재사용한다.

코어 베이스는 다음과 같다.

- `SingletonBase` / `Singleton<T>` — 제네릭 싱글톤 베이스 (2단 구조, [2장](#2-싱글톤-베이스) 참고)
- `Logger` — 화면 오버레이 디버그 로거 (`Singleton<Logger>` 상속)

그 위에 `GameManager`, `Define`, `DataManager`를 얹어 코어 골격을 완성한다.

> **프로젝트 전제 (컨셉 기획서 v0.1 확정)**: 2D 캐주얼 모바일(Android, 세로 화면), Unity 6.3 LTS, **싱글플레이 — 네트워크 미사용**. 게임은 「총알소녀」 — 3-Sort로 포탑을 소환해 웨이브 몬스터를 막는 디펜스다. 미션 필수 기술인 **데이터 드리븐(Excel/JSON)** 구조를 코어에서 `DataManager`로 지원한다. 입력은 모바일 터치 기반이며, 입력 세부는 [6장](#6-inputmanager)을 따른다.

## 1. 코어 레이어 구성

### 1.1 의존 구조

```
SingletonBase                ← 비제네릭 베이스 (static 리셋 담당)
   └─ Singleton<T>           ← 제네릭 싱글톤 베이스
        ├─ Logger            ← 디버그 로거 (씬 배치, GameManager 자식)
        └─ GameManager       ← 매니저 생성·등록 허브
             ├─ DataManager     ← Excel/JSON 데이터 로드
             ├─ InputManager    ← 모바일 터치 입력
             └─ (그 외 매니저들) ← GameManager가 런타임 생성·등록

Define                       ← static 상수·Enum (상속 아님, 전역 참조)
```

`SingletonBase`와 `Singleton<T>`로 베이스를 2단으로 나눈 이유는 [2.1](#21-왜-2단-구조인가)을 참고한다.

### 1.2 폴더 / 네임스페이스

- 코어 코드 위치: `Assets/Project/Scripts/Core/`
  - `Core/Singletons/` — `Singleton.cs` (`SingletonBase` + `Singleton<T>`)
  - `Core/Managers/` — 각종 매니저
  - `Core/` 직하 — `Logger.cs`, `Define.cs` 등
- 네임스페이스: `Core` (코어 코드 전부)
- 범용 유틸리티는 `Scripts/Utils/`에 두며 코어와 분리한다. `Logger`는 코어 구성요소이므로 `Utils`가 아니라 `Core`에 둔다.
- 코어 코드는 **플밍 팀장이 관리**한다. 수정이 필요하면 [9장](#9-코어-코드-변경-절차)을 따른다.

### 1.3 코어가 보장하는 것

| 보장 | 내용 |
|---|---|
| 단일 인스턴스 | 매니저는 씬에 하나만 존재 |
| 씬 전환 생존 | `DontDestroyOnLoad`로 매니저 유지 |
| 종료 안전성 | 앱 종료 시 싱글톤 재생성·널 접근 방지 |
| 디버그 가시성 | `Logger`로 빌드에서도 화면 로그 확인 |
| 초기화 순서 | Script Execution Order로 순서 보장 |
| 데이터 분리 | `DataManager`로 기획 데이터를 코드와 분리 |

## 2. 싱글톤 베이스

### 2.1 왜 2단 구조인가

싱글톤 베이스는 `SingletonBase`(비제네릭)와 `Singleton<T>`(제네릭) 두 클래스로 나뉜다.

이유는 **도메인 리로드를 꺼도 안전하게** 만들기 위해서다. 에디터에서 도메인 리로드를 끄면 플레이를 다시 시작해도 `static` 필드가 이전 플레이 값을 유지한다. `_isQuitting`이 `true`로 남으면 싱글톤이 계속 `null`을 반환하는 버그가 생긴다. 이를 막으려면 `[RuntimeInitializeOnLoadMethod]`로 `static`을 리셋해야 하는데, **이 어트리뷰트는 제네릭 클래스 안에 둘 수 없다.** Unity가 어떤 `T`로 호출할지 정할 수 없기 때문이다.

그래서 리셋 로직을 비제네릭 `SingletonBase`로 분리한다.

- `SingletonBase` — `_isQuitting`, 리셋 레지스트리, `[RuntimeInitializeOnLoadMethod]` 보유
- `Singleton<T>` — 타입별 `_instance`, 인스턴스 수명 관리

각 `Singleton<T>`는 자기 `_instance`를 비우는 함수를 `SingletonBase`의 레지스트리에 등록하고, 플레이 진입 시 `SingletonBase`가 등록된 모든 리셋을 실행한다. 이 구조 덕분에 도메인 리로드 설정과 무관하게 항상 깨끗한 상태로 시작한다.

> `Singleton<T>`에는 `[RuntimeInitializeOnLoadMethod]` 메서드가 없어 분석기가 UDR0001 경고를 띄울 수 있다. 제네릭 우회 설계상 불가피하며, 리셋은 `SingletonBase`가 처리하므로 **의도된 설계다. 무시한다.**

### 2.2 사용법 — 자식은 `Init()`을 오버라이드한다

매니저는 `Singleton<T>`를 상속한다. **자식은 `Awake`를 건드리지 않고 `Init()`을 오버라이드한다.**

> ⚠ **플밍 파트 합의 규약**: 모든 매니저는 `Init()`을 오버라이드하고 `Awake`는 손대지 않는다. 이는 선택이 아니라 약속이다. 코드 리뷰에서 자식이 `Awake`를 오버라이드한 게 발견되면 `Init()`으로 교체를 요청한다. 예외가 필요하면 플밍 팀장과 사전 협의.

```csharp
public class GameManager : Singleton<GameManager>
{
    protected override void Init()
    {
        // 초기화 코드 — 살아남은 단일 인스턴스에서만 실행됨
    }
}
```

`Awake`는 `Singleton<T>`가 가져간다. 베이스 `Awake`가 중복 인스턴스를 걸러내고, **살아남은 단일 인스턴스에서만 `Init()`을 호출**한다. 따라서 자식은 `base.Awake()` 호출이나 중복 체크를 직접 할 필요가 없다 — 그 책임이 베이스로 옮겨졌다.

### 2.3 핵심 동작

- **인스턴스 접근**: `Instance`로 접근한다. 씬에 없으면 `FindFirstObjectByType<T>()`로 탐색하고, 그래도 없으면 런타임에 자동 생성한다. 자동 생성된 오브젝트는 하이어라키에서 `[Singleton] 클래스명`으로 표시된다.
- **종료 가드(`_isQuitting`)**: 앱 종료 시 싱글톤 파괴 순서는 보장되지 않는다. 이미 파괴된 싱글톤이 재생성되는 것을 막기 위해, 종료 상태에서는 `Instance`가 `null`을 반환한다. `_isQuitting`은 모든 싱글톤이 공유한다 — "앱 전체가 종료 중인가"라는 의미라 공유가 맞다. 외부에서는 `IsQuitting`으로 확인한다.
- **`DontDestroyOnLoad` 조건부 호출**: 루트 오브젝트일 때만 호출한다. `GameManager`의 자식으로 배치되는 싱글톤(예: `Logger`)은 부모를 따라가므로 별도 호출이 불필요하다.
- **중복 인스턴스 처리**: 씬에 같은 싱글톤이 둘 이상 있으면, 나중 인스턴스는 경고 로그 후 자동으로 `Destroy`되며 `Init()`이 호출되지 않는다. 중복 인스턴스가 초기화 코드를 실행하는 사고가 구조적으로 막힌다.
- **`OnDestroy` 정리**: 인스턴스가 파괴되면 `_instance`를 비운다. 단 `if (_instance == this)`로 가드하여, 중복 인스턴스가 파괴될 때 살아있는 진짜 인스턴스의 참조는 건드리지 않는다.

### 2.4 리셋 레지스트리 주의

`Singleton<T>`는 `_instance`를 비우는 리셋 함수를 `SingletonBase`의 `HashSet`에 등록한다. 이때 리셋 함수(`_resetInstance`)는 **`static readonly`로 한 번만 만들어 재사용**해야 한다. 람다를 매번 새로 만들면 참조가 달라져 `HashSet`의 중복 판정이 무력화된다. 코어 코드를 수정할 때 이 전제를 깨지 않는다.

### 2.5 종료 시 이벤트 해제

이벤트를 구독하는 매니저는 종료 시 구독 해제를 시도하다 이미 파괴된 싱글톤에 접근할 수 있다. 이때 `IsQuitting`으로 가드한다.

- `Singleton`을 상속한 클래스: `IsQuitting` 프로퍼티 직접 사용.
- 일반 `MonoBehaviour`: `SingletonBase.IsQuitting` 또는 `Singleton<대상>.IsQuitting`으로 접근.
- 자식이 `OnDestroy`를 오버라이드할 때는 `base.OnDestroy()`를 호출해야 베이스의 `_instance` 정리가 실행된다.

```csharp
protected override void OnDestroy()
{
    base.OnDestroy(); // 베이스의 _instance 정리

    if (IsQuitting) return; // 종료 중이면 구독 해제 스킵
    SomeManager.Instance.OnSomething -= Handler;
}
```

## 3. Logger

### 3.1 역할

`Singleton<Logger>`를 상속한 화면 오버레이 디버그 로거. `Debug.Log`와 달리 **빌드에서도** 화면에 로그가 보이므로, 에디터 밖 동작 확인에 쓴다. 모바일 빌드(APK)를 실기기에서 디버깅할 때 특히 유용하다.

### 3.2 구성

- 스크립트: `Core/Logger.cs`, 네임스페이스 `Core`.
- UI 프리팹: `Project/Prefabs/`에 `Canvas + TextMeshProUGUI` 오버레이 프리팹으로 둔다. 배경 반투명 처리로 게임 화면을 가리지 않는다.
- `Queue<string>` 기반 선입선출 관리. 최대 라인 수(`maxLines`, 기본 15)를 초과하면 가장 오래된 로그가 자동 제거된다.
- 로그 타입별 색상 + `HH:mm:ss.fff` 타임스탬프.

### 3.3 사용법

```csharp
Logger.Instance.LogInfo("스테이지 시작");         // 초록
Logger.Instance.LogWarning("데이터 누락 가능성");  // 노랑
Logger.Instance.LogError("3-sort 슬롯 계산 실패"); // 빨강
Logger.Instance.Clear();                          // 화면 로그 비우기
```

### 3.4 동작 조건 / 주의

- **초기화는 `Init()` 오버라이드**: `Logger`는 `Singleton<Logger>`를 상속하므로 `Awake`가 아니라 `Init()`에서 초기화한다. ([2.2](#22-사용법--자식은-init을-오버라이드한다) 참고.)
- **릴리즈 빌드에서는 비활성**: `Debug.isDebugBuild`가 `false`면 `Init()`에서 게임오브젝트를 끈다. 유닉온 제출용 릴리즈 APK에 디버그 UI가 노출되지 않는다.
- **에디터 토글**: `#if UNITY_EDITOR` + `OnValidate`로, 인스펙터의 `enableDebug` 체크박스를 켜고 끄면 텍스트 표시가 즉시 바뀐다.
- **프리팹 형태로 씬에 배치**한다. UI 캔버스를 포함하므로 `GameManager`의 런타임 자동 생성 대상이 아니다. ([8장](#8-script-execution-order) 참고.)
- 코어 자체 메시지나 치명 오류는 화면 로그에 의존하지 말고 `Debug.LogError`도 병행한다. (Logger가 꺼진 상황 대비.)

## 4. GameManager

### 4.1 역할

`Singleton<GameManager>`를 상속한 **매니저 생성·등록 허브**. 프로젝트에서 필요한 매니저들을 런타임에 생성하고 자신의 자식으로 등록한다. 매니저들이 `GameManager` 아래 묶이면 하이어라키가 정리되고, 부모의 `DontDestroyOnLoad`를 함께 따라간다.

### 4.2 매니저 등록 패턴

`GameManager`는 `Init()`에서 필요한 매니저를 일괄 등록한다. 등록 헬퍼는 매니저를 생성해 `GameManager`의 자식으로 붙인다. `Init()`은 베이스가 살아남은 단일 인스턴스에서만 호출하므로, 중복 체크를 직접 할 필요가 없다. ([2.2](#22-사용법--자식은-init을-오버라이드한다) 참고.)

```csharp
protected override void Init()
{
    RegisterManager<DataManager>();   // 데이터 먼저 로드
    RegisterManager<InputManager>();
    RegisterManager<AudioManager>();
    // 게임플레이 매니저는 인게임 씬 구성에 맞춰 추가
}
```

- **순수 코드 매니저**(UI·프리팹 없음)는 `RegisterManager`를 통한 런타임 자동 생성에 적합하다. `DataManager`, `InputManager`가 여기 해당한다.
- **UI·프리팹을 포함한 싱글톤**(예: `Logger`)은 자동 생성 대상이 아니다. 씬에 프리팹으로 직접 배치한다.
- `DataManager`는 다른 매니저가 데이터를 참조할 수 있으므로 **가장 먼저 등록**한다.

### 4.3 책임 범위

- `GameManager`는 **매니저 등록과 전역 진입점** 역할에 집중한다.
- 게임 규칙·상태 흐름은 `GameManager`에 몰아넣지 않고 별도 매니저로 분리한다. 「총알소녀」 기준 분리 대상은 다음과 같다.
  - **인게임 흐름 매니저** — 웨이브 진행(10웨이브), 정비 시간, 클리어/게임오버 판정. `GamePhase` Enum([5장](#5-define))으로 상태를 관리한다.
  - **3-Sort / 슬롯 매니저** — 슬롯 컨테이너 상태, 같은 기물 3개 도달 판정, 포탑 소환 트리거.
  - **전투 / 스폰 매니저** — 몬스터 스폰·이동, 포탑 공격.
  - 위 매니저들은 인게임 씬에서만 필요하므로, 전역 싱글톤이 아니라 인게임 씬 범위로 둘지 코어 싱글톤으로 둘지는 데모 설계 시 결정한다.
- 이 프로젝트는 씬 구성이 단순하다(로비 / 인게임 / 정산). 별도 씬 매니저 없이 `GameManager`에 씬 전환 함수를 두는 것을 허용한다. 씬이 늘어나면 분리한다.

### 4.4 ⚠ 씬마다 GameManager를 배치할 때

`GameManager`를 여러 씬(로비·인게임 등)에 프리팹으로 배치하면, 씬 로드 시 중복 인스턴스가 생긴다. 새 싱글톤 구조에서는 베이스 `Awake`가 중복 인스턴스를 자동으로 걸러내고 `Init()`을 호출하지 않으므로, 중복 `GameManager`가 매니저를 잘못 등록하는 사고가 구조적으로 막힌다. ([2.2](#22-사용법--자식은-init을-오버라이드한다)·[2.3](#23-핵심-동작) 참고.) 자식이 `Awake`를 건드리지 않고 `Init()`만 오버라이드하면 된다.

## 5. Define

### 5.1 역할

전역적으로 쓰는 **상수(Constant)와 열거형(Enum)**을 한곳에 모은다. 상속용 클래스가 아니라, `static` 멤버로 참조하는 정의 모음이다.

### 5.2 작성 규칙

- 상수는 `UPPER_CASE`, Enum 타입은 `PascalCase`.
- 매직 넘버·매직 스트링(태그·레이어 이름·씬 이름 등)을 코드에 직접 쓰지 말고 `Define`에 모아 오타를 방지한다.
- 특정 시스템에서만 쓰는 Enum은 그 시스템 파일에 두어도 된다. **두 개 이상 시스템이 공유**하는 것만 `Define`에 올린다.

```csharp
namespace Core
{
    public static class Define
    {
        // 씬 이름
        public const string SCENE_LOBBY = "Lobby";
        public const string SCENE_INGAME = "InGame";
        public const string SCENE_RESULT = "Result";

        // 게임 진행 고정 규칙 (기획 확정값 — 변동 가능성 있으면 데이터로)
        public const int WAVE_PER_STAGE = 10;     // 스테이지당 웨이브 수
        public const int SORT_COUNT = 3;          // 정렬 완성에 필요한 기물 수
    }

    public enum SceneType { Lobby, InGame, Result }
    public enum Language { KO, EN }       // 인게임 텍스트 시트 현지화
    public enum GamePhase { Wave, Intermission, Cleared, GameOver } // 인게임 흐름
}
```

> 게임플레이 수치(몬스터 HP, 경험치 곡선, 포탑 공격력, 특전 효과, 웨이브 몬스터 배치 등)는 `Define` 상수가 아니라 **데이터 시트**([7장](#7-datamanager-데이터-드리븐))로 관리한다. `Define`에는 코드 구조에 관한 고정값만 둔다. 웨이브 수·정렬 개수처럼 거의 바뀌지 않는 규칙 상수는 `Define`에 두되, 밸런싱 대상이 되면 데이터로 옮긴다.
>
> **기물·포탑·몬스터의 종류 Enum**(예: 포탑 종류)은 종류 수가 기획에서 확정되는 대로 정의한다. 컨셉 기획서 기준 포탑은 7종(권총·샷건·로켓·레이저·스나이퍼·기관총·둔화) 방향이나, 데모 범위에서는 일부만 구현할 수 있으므로 데모 착수 시 확정한다.

## 6. InputManager

### 6.1 역할

`Singleton<InputManager>`를 상속한 모바일 입력 매니저. 이 프로젝트의 핵심 조작은 **3-sort 슬롯에 아이템을 드래그해 넣는 터치 조작**이다. `InputManager`는 터치/드래그 입력을 받아 이벤트로 발행하고, 각 시스템은 이를 구독한다.

### 6.2 입력 방식

- Unity **Input System** 패키지를 사용한다. (Unity 6.3 LTS 권장.)
- 터치·드래그 입력을 받아 이벤트로 발행한다(명칭은 구현 시 확정): 터치 시작, 드래그 중, 터치 종료.
- 드래그 대상(기물)·드롭 위치(슬롯) 판정은 입력 좌표를 받은 게임플레이 측에서 처리한다. `InputManager`는 **입력 신호 발행까지만** 책임진다.

### 6.3 좌표계 — 게임플레이는 월드 스페이스

게임플레이 요소(슬롯·기물·포탑·몬스터)는 **월드 스페이스의 SpriteRenderer**로 구현한다. 적과의 충돌·공간 상호작용이 있어 UI 캔버스로 두면 좌표계가 분리되기 때문이다.

- 게임플레이 → 월드 스페이스 SpriteRenderer, `Collider2D` 충돌 사용.
- 정보 UI(체력·경험치 게이지, 목표·시간 표시, 일시정지·특전 팝업, 로비, 정산) → UGUI.
- `InputManager`는 터치 스크린 좌표를 발행하고, 게임플레이 측이 `ScreenToWorldPoint`로 월드 좌표를 얻어 기물 드래그·슬롯 판정에 쓴다.

> 이전 매치-3 프로젝트의 `BlockDragHandler`는 UGUI(`RectTransform`/`anchoredPosition`) 기반이었다. 「총알소녀」 이식 시 좌표계를 월드 스페이스로 바꿔야 한다. 드래그 로직 흐름(오프셋 계산·클램핑·하이라이트)은 재사용하되 좌표 변환 레이어를 교체한다.

### 6.4 설계 규칙

- 한 번만 소비되어야 하는 입력은 매 프레임 폴링하지 말고 **이벤트 기반**으로 발행한다. 구독자가 상태 변경 시점에만 반응하게 하여 `Update` 폴링을 줄인다.
- UI 위 터치와 게임플레이 터치를 구분해야 하면 `EventSystem`의 포인터 판정(`IsPointerOverGameObject`)을 활용한다.
- 이벤트 구독자는 종료 시 반드시 해제한다. ([2.4](#24-종료-시-이벤트-해제) 참고.)

## 7. DataManager (데이터 드리븐)

### 7.1 역할

미션 가이드의 필수 기술 — **데이터와 코드의 분리(데이터 드리븐)** — 를 담당하는 코어 매니저. 「총알소녀」는 데이터 테이블이 많은 게임이다. 스테이지·웨이브별 몬스터 배치, 몬스터 스탯, 포탑 스탯, 기물 정의, 경험치 곡선, 특전(강화) 풀, 인게임 텍스트 등 **기획이 조정하는 값**을 코드 밖 데이터로 두고, `DataManager`가 이를 로드해 게임에 공급한다.

예상 데이터 테이블(기획과 스키마 합의 후 확정):

| 테이블 | 내용 |
|---|---|
| 기물 | 종류, 스프라이트, 대응 포탑 |
| 포탑 | 종류, 공격 방식, 공격력·사거리·속도 |
| 몬스터 | 유형, HP, 이동 속도, 처치 보상 경험치 |
| 웨이브 | 스테이지·웨이브별 몬스터 등장 배치·타이밍 |
| 특전(강화) | 분류, 효과, 등장 조건 |
| 경험치 | 레벨별 필요 경험치 곡선 |
| 텍스트 | 한/영 인게임 텍스트 |

> 미션 요건: "데이터와 코드는 반드시 분리한 데이터 드리븐 형태로 제작 (Excel 또는 JSON)". 또한 최종 산출물에 **메타데이터가 정리된 JSON/Excel 파일**이 포함되어야 한다.

### 7.2 데이터 파이프라인

```
기획(Google Spreadsheet)  →  Excel/CSV 내보내기  →  JSON 변환
                                                       ↓
                          DataManager가 런타임 로드 → 각 시스템에 공급
```

- **원본 관리**: 기획 데이터의 원본은 Google Spreadsheet(미션 지정 문서 관리 도구)에서 관리한다.
- **런타임 포맷**: 게임이 읽는 최종 포맷은 JSON으로 통일한다. Excel/CSV는 중간 편집본으로 두고, JSON으로 변환해 지정 데이터 폴더에 둔다.
- **로드 시점**: `DataManager`는 `GameManager`가 가장 먼저 등록하며, 다른 매니저보다 앞서 데이터를 로드한다.

### 7.3 설계 규칙

- 각 데이터 테이블은 **직렬화용 클래스(DTO)**로 1:1 대응시킨다. 코드에 수치를 하드코딩하지 않는다.
- 데이터 키(스테이지 ID, 몬스터 ID 등)는 문자열 오타를 막기 위해 로드 시점에 유효성 검사를 한다. 누락·중복 키는 `Logger.LogError`로 즉시 드러낸다.
- **인게임 텍스트**는 한/영 시트로 분리해 관리한다(미션 필수 기능 — 현지화). `Language` Enum([5장](#5-define))으로 현재 언어를 선택하고, 텍스트 조회는 `DataManager`를 거친다.
- 데이터 스키마(시트 컬럼 구성)가 바뀌면 DTO 클래스도 함께 바꾸고 기획 파트에 공유한다. **스키마는 기획-개발 합의 사항**이다.

### 7.4 기획 협업 주의

- 데이터 시트의 컬럼명·타입·키 규칙은 기획과 **사전 합의**한다. 합의 없이 한쪽이 시트 구조를 바꾸면 로드가 깨진다.
- 데이터만 바꿔서 되는 변경(수치 조정 등)은 코드 수정 없이 시트 갱신 → JSON 재변환으로 끝나야 한다. 이것이 데이터 드리븐의 목적이다. 데이터 변경에 매번 코드 수정이 필요하다면 구조가 잘못된 것이다.

## 8. Script Execution Order

### 8.1 왜 필요한가

`Logger`는 UI 캔버스를 포함한 프리팹이라 씬에 직접 배치된다. 다른 매니저가 초기화(`Init()`) 중 `Logger.Instance`를 호출할 수 있으므로, `Logger`의 초기화가 먼저 실행되어야 한다.

### 8.2 설정

`Edit > Project Settings > Script Execution Order`에서 다음 순서를 보장한다.

| 순서 | 스크립트 | 이유 |
|---|---|---|
| 먼저 | `Logger` | 다른 매니저가 초기화 중 로그를 남길 수 있음 |
| 다음 | `GameManager` | 매니저 등록 허브 (`DataManager`를 가장 먼저 등록) |
| 기본 | 그 외 | 기본값 |

> 매니저 간 초기화 순서(`DataManager`를 먼저)는 `GameManager`의 `Init()` 안 등록 순서로 제어한다. Script Execution Order는 `Logger`·`GameManager`처럼 씬에 배치되는 스크립트의 순서만 다룬다. 순서 의존은 최소화하고, 가능하면 명시적 초기화 호출로 푼다.

## 9. 코어 코드 변경 절차

코어 코드(`Singleton.cs` 의 `SingletonBase`·`Singleton<T>`, `Logger`, `GameManager`, `Define`, `DataManager`, `InputManager`)는 플밍 파트 전원이 의존하므로 변경 영향이 크다.

1. 변경 필요 시 플밍 팀장에게 사유와 함께 공유한다.
2. 별도 브랜치(`refactor/core-*_작성자`)에서 작업한다.
3. 변경 후 매니저 초기화·씬 전환·앱 종료를 테스트한다.
4. PR로 올리고, 머지 시 소통 채널에 **코어 변경**임을 명시 통보한다.
5. 변경 내용을 이 문서와 작업 노트에 반영한다.
