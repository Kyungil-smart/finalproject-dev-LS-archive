# 총알소녀 데모 역할 분담 회의 자료

## 회의 안내

> 데모(~06/08) 구간의 플밍 역할을 정하기 위한 자료다. 각자 어떤 영역을 가져갈지
> 이 문서를 보면서 함께 결정한다.
>
> - 큰 묶음(A·B·C…) 단위로 통째로 가져가도 되고, 세부 항목 단위로 쪼개 가져가도 된다.
> - 한 사람이 여러 묶음을 가질 수 있고, 한 묶음을 둘이서 나눠 가질 수도 있다.
> - 데모 일정상 **인프라(묶음 A)와 3-Sort(묶음 B)는 가능한 한 같은 사람이 잡는 게 좋다**.
>   둘이 인터페이스가 가장 많이 얽힌다.
> - 가챠(외부 시스템)는 데모 후순위. 인게임 핵심 루프 완성 후 시간 허락 시 착수.
> - 모든 시스템은 **이벤트 기반** 연결을 권장(직접 참조 최소화).

회의 진행 방식:

1. 묶음 6개 훑어보기
2. 각자 가져가고 싶은 묶음·항목에 이름 표시
3. 충돌·공백 조정
4. 인터페이스(시스템 간 이벤트) 합의 일정 정하기 (데모 첫 주 안)
5. 결정된 분담을 별도 「데모 역할 분담 확정본」 문서로 정리

## 묶음 B — 3-Sort 슬롯·기물 시스템 (이성규)

> 게임의 중심 메커닉. 정렬 → 포탑 소환의 진입점.

**규모**: 대 / **선행 작업**: 묶음 A 일부 (`InputManager`, `DataManager`) / **권장 인원**: 1인 (인프라 담당과 동일 인원 권장)

| | 세부 항목 | 비고 |
|---|---|---|
| ☐ | 슬롯 데이터 구조 (월드 스페이스 SpriteRenderer 기반) | 게임플레이는 월드 스페이스 |
| ☐ | 기물 SO 정의 (타입·스프라이트) | 매치-3 `BlockDataSO` 재활용 가능 / G-2 표준 따름 |
| ☐ | 기물 드래그 핸들러 | 매치-3 `BlockDragHandler` 포팅 (UGUI → 월드) |
| ☐ | 같은 기물 3개 도달 판정 → 포탑 소환 이벤트 발행 |  |
| ☐ | 슬롯 HP 관리 |  |
| ☐ | 슬롯 파괴 (HP 0) — 기물 저장·이동은 가능 |  |
| ☐ | 슬롯 수리 (파괴 슬롯에서 소팅 여러 번 → 수리) |  |
| ☐ | 소팅 성공 시 슬롯 체력 소량 회복 |  |
| ☐ | 모든 슬롯 파괴 = 게임오버 이벤트 발행 |  |
| ☐ | **보드 클리어 보너스** — 모든 슬롯 기물 비움 시: 필드 전체 적에게 데미지 + 슬롯 리필 | 신규 메커닉 |
| ☐ | 리롤 (화면 + 예비 블럭 전체 섞어 재배치) | 후순위 가능 |

## 묶음 G — 데이터 드리븐 (기획 확정 이후)

> 미션 필수 기술. 각 시스템 담당이 자기 SO를 만들 때 따를 **표준과 파이프라인**을 잡는 묶음.
> SO 정의 자체는 각 시스템 담당이 하되, 이 묶음 담당이 스키마 표준을 합의·관리한다.

**규모**: 중 / **선행 작업**: 묶음 A 일부 (`GameManager`) / **권장 인원**: 1인

### G-1. 파이프라인 (이 묶음 담당 단독)

| | 세부 항목 | 비고 |
|---|---|---|
| ☐ | `DataManager` — JSON 로드, 타입별 SO 공급 | 다른 매니저보다 먼저 등록 |
| ☐ | Excel/CSV → JSON 변환 도구 (또는 흐름 합의) | `Data/Source/` → `Data/Json/` |
| ☐ | 데이터 폴더 구조와 명명 규칙 | `Project/Data/` 하위 |
| ☐ | Addressables 연계 검토 (또는 Resources 방식 확정) |  |
| ☐ | 로드 시점 유효성 검사 (누락·중복 키 → Logger.LogError) |  |
| ☐ | 인게임 텍스트 시트 (한/영 현지화) — `Language` Enum 연계 |  |

### G-2. 스키마 표준 (첫 주 안에 합의 — 각 시스템 담당과 함께)

| | 세부 항목 | 책임 합의 대상 |
|---|---|---|
| ☐ | 키 명명 규칙 (스테이지 ID, 몬스터 ID, 포탑 ID, 특전 ID 등) | 전원 |
| ☐ | 공통 필드 + 타입 의존 필드 SO 구조 — (a) 단일 SO + 옵션 필드 / (b) 베이스 + 파생 SO | C-2(포탑) 담당과 |
| ☐ | DTO 클래스 작성 규약 (시트 컬럼 ↔ C# 필드 매핑) | 전원 |
| ☐ | 데이터 변경 시 스키마 동기화 절차 (기획팀과의 합의 포함) | 전원 |

### G-3. SO 정의 — 각 시스템 담당이 G-2 표준 따라 작성

이 묶음 담당은 직접 만들지 않고, 표준 준수 여부만 점검한다.

## R&D 진행 방향 (각자 구현 영역별)

회의 후 각자 자기 영역의 R&D를 진행한다. 위 묶음의 세부 항목 중 **R&D 대상**으로
표시된 것을 중심으로, 데모 코드 착수 전 필요한 사전 조사·실험을 진행한다.

| 담당 | R&D 방향 |
|---|---|
| 이성규 (팀장) | 각종 문서 작성. 추후 예시 `GameManager` 작성. |
| 김경민 (D·E) | R&D보다는 **docs 정독으로 기획 이해**, 이벤트 구조 연결 이해, 시스템 설계 사고. 로그라이크는 다른 시스템의 출력을 받아 처리하는 위치라 인터페이스 이해가 코드보다 우선. |
| 안정연 (C-2) | **포탑 타깃 서칭 방식** R&D. 거리순 우선순위(가장 먼/가장 가까운) 후보 탐색·캐싱 전략, 매 프레임 부하 최소화. |
| 연동준 (C-1) | **오브젝트 풀링** R&D. 누적 처치 수천 단위에 견디는 몬스터·발사체 풀 구조. |

데모 시작 전 첫 주 안에 다음 항목을 확정한다.

- [ ] 묶음·세부 항목 담당 배정
- [ ] 인터페이스(시스템 간 이벤트) 시그니처 합의 — 누가 누구에게 어떤 이벤트를 보내는가
- [ ] 회의에서 결정된 내용을 「데모 역할 분담 확정본」으로 별도 문서화

이 회의 자료는 결정 후 폐기하거나, 결정본 문서 부록으로 보관한다.
