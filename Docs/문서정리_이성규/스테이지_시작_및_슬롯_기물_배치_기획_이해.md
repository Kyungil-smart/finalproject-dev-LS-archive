**원본 문서**: 스테이지 시작 및 슬롯 기물 배치 기획서 v1.4 (임소영)
**정리 작성**: 이성규

**용도**: 구현 진입 전 기획 룰·의도·데이터 규모를 코드 결정에 직접 활용 가능한 형태로 정리

## 1. 시스템 전체 구조

게임 진입 시 *고정 설정*이 1회 실행되고, 이후 *반복 생성 사이클*이 스테이지 종료까지 돈다.

```
시작
  ↓
[게임 진입 고정 설정] (1회)
  ├─ 슬롯 생성 및 배치 (3×3 = 9슬롯, 모든 스테이지 동일 위치)
  └─ 기물 세트 설정 (종류·개수·1세트 크기)
  ↓
[반복 생성 사이클]
  ├─ 기물 대기 그룹 저장 (생성된 세트를 내부 DB에)
  ├─ 기물 슬롯 랜덤 배치 (초기 배치 — 슬롯당 2개)
  ↓
  ┌─ 빈 슬롯 감지 ──────────────────────────────┐
  │   ↓                                          │
  │   [대기 기물 존재?]                          │
  │     ├─ Yes → 우선순위 배치 → 칸 선정 → 배치─┤
  │     └─ No  → [슬롯 내 기물 전체 처리?]       │
  │                ├─ Yes → 기물 세트 재생성 ────┘
  │                └─ No  → "생성되지 않음" (대기)
  └────────────────────────────────────────────────
  ↓
[스테이지 종료 여부]
  ├─ No  → 사이클 진행 → 빈 슬롯 감지로 루프
  └─ Yes → 스테이지 종료
```

## 2. 데이터 규모

### 2-1. 슬롯

| 항목 | 값 |
|---|---|
| 슬롯 배치 | 3×3 |
| 슬롯 총 개수 | 9개 |
| 전체 기물 배치 가능 슬롯 칸 수 | 27칸 |

### 2-2. 1개 슬롯 공용 정보

| 항목 | 값 |
|---|---|
| 슬롯 배치 최소 기물 수 | 0개 |
| 슬롯 배치 최대 기물 수 | 3개 |
| 슬롯 1칸에 배치 가능한 기물 수 | 1개 |

### 2-3. 기물 세트 (4-3절 예시 설정 — 변동 가능)

| 기물 종류 | 1세트 개수 | 스테이지 배치 세트 수 | 총 개수 |
|---|---|---|---|
| A기물 | 3 | 3 | 9 |
| B기물 | 3 | 3 | 9 |
| C기물 | 3 | 3 | 9 |
| D기물 | 3 | 3 | 9 |
| E기물 | 3 | 3 | 9 |
| F기물 | 3 | 3 | 9 |
| **합계** | | | **54** |

**핵심 의미**:
- 한 라운드 풀 크기 = 54개
- 초기 슬롯 배치 18개 + 대기 그룹 36개 = 54
- *54는 27칸의 정확히 2배* — 슬롯이 한 번 완전히 채워졌다가 비워지는 두 번의 사이클을 가정한 수치

**기획 명시**:
- 4-3절 표는 *설계 방향성 설명용 예시 설정*이며, *스테이지 배치 기물 세트 개수*는 추후 콘텐츠 설계 시 변경 가능
- 즉 *기물 종류 수·1세트 개수·스테이지 세트 수* 셋 다 데이터 드리븐 대상

## 3. 룰 정리 — 12개 핵심 규칙

### 3-1. 슬롯·셀 기본

1. 모든 슬롯은 3개의 칸을 가지고, 1개의 칸에는 1개의 기물만 들어감
2. 슬롯 위치는 모든 스테이지에 *고정* (동적 배치 아님)

### 3-2. 초기 배치 (6절)

3. **슬롯 칸 선정** — 슬롯 내 1·2·3번째 칸 중 어느 위치에 기물 배치할지 *각 슬롯 별로 랜덤*하게 선정. **3개 칸 중 2개 칸을 선정**
4. **기물 선정** — *대기 기물 그룹*에서 *슬롯 별로 기물 2종 선정*, 총 18개의 기물이 슬롯에 배치
5. **확률 시스템** — 슬롯당 *3개 배치* 확률 시스템이 있으나 *데모는 0%로 배제* 합의됨 (5-1절 참고 사항)

### 3-3. 대기 그룹

6. *기물 대기 그룹*은 시스템 내부 DB의 비공개 풀, 유저에게 표시되지 않음
7. *대기 그룹에 있는 기물 안에서만* 슬롯 칸에 배치 가능
8. 슬롯 배치로 선정되면 대기 그룹에서 *제거*되고 슬롯으로 이동

### 3-4. 정렬·이동

9. **3Sort 성공** — 슬롯 내 동일 기물 3개 모이면 슬롯의 셀 데이터는 Empty로 초기화, 정렬 데이터(SlotID, PieceID)를 포탑 소환 시스템으로 전달
10. **기물 이동** — 다른 슬롯의 빈 칸으로 드래그·드롭. 빈 칸 아니면 *원위치 복귀*
11. **빈 슬롯 발생 상황** — ① 3Sort 성공한 슬롯, ② 기물을 다른 슬롯으로 이동시켜 슬롯에 남은 기물이 없음

### 3-5. 재생성 조건 (8절)

12. **재생성 AND 조건** — 다음 둘 *모두* 만족 시에만 기물 세트 재생성
    - 조건1: 대기 그룹에 남은 기물 없음
    - 조건2: 모든 슬롯에 배치된 기물 없음
    - 하나라도 미달성 시 *"기물 대기 그룹에 기물이 생성되지 않음"* 상태로 대기 (페이스 조절 메커니즘)

## 4. 우선순위 배치 알고리즘 (9절)

### 4-1. 의도

**핵심 키워드: 끊기지 않는 흐름**

- 단순 랜덤은 *현재 슬롯 상태와 무관한 기물*을 줄 수 있음 → 데드락 가능성 ↑, 유저 판단력 요구 ↑
- AI 시뮬레이션 결과:
  - 초기 배치 데드락은 *거의 0%*
  - 저점 유저(큰 생각 없이 퍼즐하는 유저) 데드락: *10~20%*
- *유저가 콤보 유지 방향을 쉽게 인지*하고 *짧은 시간 안에 다음 정리 목표를 판단*할 수 있도록 기준 설계

**서브 의도** — 동일 기물이 보드 전체에 *정확히 3개*만 배치된 경우:
- 유저가 해당 기물을 정리 대상으로 인지 못 할 수 있음
- 다음 배치에서 동일 기물 추가 → 4개로 늘리면 존재감 ↑
- 즉시 완성 가능한 조합뿐 아니라 *다음 콤보 후보*까지 자연스럽게 제시

### 4-2. 선정 우선 순위

| 순위 | 설명 |
|---|---|
| 1 | 모든 슬롯 내에 배치되어있는 *동일 기물이 2개*인 기물 |
| 2 | 모든 슬롯 내에 배치되어있는 *동일 기물이 3개*인 기물 |
| 3 | 기물 대기 그룹 내에서 랜덤으로 기물 선정 |

### 4-3. 예외 처리

- *첫 번째 기물*은 우선 순위 기준에 맞춰 배정
- *두 번째 기물*은 *첫 번째 기물을 포함해서* 우선 순위 기물 탐색

**예외 사유**: 이 처리 없이 시뮬레이션 시 *동일 기물이 한 슬롯 내에 배치되는 경우의 수가 많아짐*. 발생률을 최소화하기 위함.

### 4-4. 데모 단계 적용

데모는 *기물 1종(Basic)*만 사용하므로 우선순위 알고리즘이 *의미 없음*(어차피 1종만 있으니 균등 랜덤 결과 = 우선순위 결과). **알고리즘은 구현하되 데이터(기물 종류 수)로 데모/CBT 자동 전환**되도록 설계.

## 5. 기물 이동 성공 조건 (7-1B절)

### 5-1. 성공 조건

플레이어가 기물을 다른 슬롯에 옮겼다고 확정짓는 조건:
1. 선택된 기물이 핸들에 등록돼 있음
2. 이동 대상 셀이 존재
3. 대상 셀이 비어 있음

### 5-2. 실패 처리

- 드래그 중 *올바르지 않은 위치*(슬롯의 빈 칸이 아닌 위치)에 놓으면 원래 위치로 배치
- 아직 *기물이 온전히 이동되지 않은 유지 조작중*일 경우 다른 슬롯으로 옮겨가지 않은 판정
- 조작 사고 방지용

## 6. 데모 vs CBT 구현 매트릭스

기획 룰을 *기본 구조로 그대로 구현*, 데이터·종류만 데모/CBT 분기. 코드 재작성 없이 데이터 교체로 확장.

| 영역 | 데모 (1라운드 짧게) | CBT (정식) |
|---|---|---|
| 기물 종류 | Basic 1종만 사용 | A~F 6종 |
| 1세트 개수 | 데이터 SO에 정의 | 데이터 SO에 정의 |
| 스테이지 배치 세트 수 | 데이터 SO에 정의 | 데이터 SO에 정의 |
| 풀 크기 | (예: 9개로 충분) | 54개 |
| 슬롯당 초기 배치 수 | 2개 (3개 배치 확률 0%) | 2개 (확률 시스템은 별도 결정) |
| 슬롯 칸 선정 | 3칸 중 2칸 랜덤 셔플 | 동일 |
| 우선순위 알고리즘 | 구현은 활성, 1종이라 결과는 랜덤과 동일 | 정식 동작 |
| 재생성 조건 | 짧은 데모에선 안 닿음 | 본격 동작 |
| 페이스 조절 (대기 0 + 슬롯 잔존 → 대기) | 룰 유지 | 룰 유지 |

**전환 방식**: 데이터 SO의 *기물 종류 수*와 *세트 개수*만 변경. 코드 분기 없음.

## 7. 구현 책임 분담 (이성규 묶음 B)

### 7-1. 본인 구현 영역

| 컴포넌트 | 책임 |
|---|---|
| `SlotBoardManager` | 9슬롯 + 대기 그룹 + 초기 배치 + 빈 칸 보충 + 재생성 조건 + 정렬 성공 외부 발행 |
| `Slot` | 셀 3개 보유 + 정렬 판정 + 셀 변경 이벤트 발행 |
| `SlotCell` | 드롭 진입점 + 배치 기준점 (이미 구현) |
| `Piece` | 드래그·드롭·기물 ID 표현 (이미 구현) |
| `WaitingGroup` | 기물 풀 자료구조 (대기 그룹 본체) |
| `PieceSelector` | 우선순위 배치 알고리즘 — 단위 테스트 가능하도록 분리 |

### 7-2. 외부 인터페이스 (안정연 영역 — 묶음 C-2)

```
SlotBoardManager.OnSortSuccess (이벤트)
   ↓ 발행
   (SlotID, PieceID)
   ↓ 구독
포탑 소환 시스템 (안정연)
   - PieceID → PieceData.ConnectTower → TowerData 조회
   - SlotID 위치에 포탑 소환
```

본인은 *PieceID 발행*까지만, *어떤 포탑이 소환되는지*는 안정연 책임. 데이터 차원에서 자연스럽게 분리됨.

### 7-3. 데이터 의존 (김경민 영역 — 묶음 G)

| 데이터 | 필요 시점 |
|---|---|
| `PieceData` SO (PieceID·PieceName·PieceSprite·ConnectTower) | 데모는 임시 enum, CBT 정식 |
| 기물 세트 설정 (종류·1세트 개수·스테이지 세트 수) | 데이터 분류(확정/변동/폐기) 받은 후 |

데이터 분류는 김경민과 합의 후 SO 구조 결정. *변동 가능*으로 분류된 항목은 SO 구조를 유연하게.

## 9. 구현 진입 결정

**기획 룰을 데모용으로 단순화하지 않고, *데이터·종류만 데모 단계 축소*해서 같은 코드가 데모/CBT 둘 다 굴러가도록 설계**.

이유:
- 데모/CBT 전환 시 *코드 재작성 비용 0*
- 우선순위 알고리즘·재생성 조건이 *복잡하지 않아* 미리 구현해도 부담 적음
- 기획팀이 *기획 룰을 그대로 검증*할 수 있어 피드백 사이클 짧음
- CBT 들어가서 *데이터만 6종으로 늘리면* 정식 게임이 됨

**다음 작업 순서** (Day 10~):

1. `Slot` 확장 — SlotID·정렬 판정·셀 변경 이벤트
2. `WaitingGroup` 신규 — 기물 풀 자료구조
3. `PieceSelector` 신규 — 우선순위 배치 알고리즘 (단위 테스트 가능 구조)
4. `SlotBoardManager` 신규 — 흐름 통합·외부 발행
5. 데이터 SO 구조 합의(김경민) — 임시 enum 교체
