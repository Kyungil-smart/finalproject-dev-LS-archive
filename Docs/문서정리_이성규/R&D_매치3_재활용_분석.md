## 짚어둘 결정 사항

### 1. 슬롯 그리드 구조

PDF 기획안 4.1.1 슬롯 데이터 트리:
```
SlotRuntimeData
├─ SlotID
├─ HP
├─ MaxHP
├─ SlotState (Normal/Locked/Destroyed/Repairing)
├─ RepairCount
└─ CellRuntimeData
   ├─ Cell1 → PieceID
   ├─ Cell2 → PieceID
   └─ Cell3 → PieceID
```

→ Day 4 결정 (슬롯 GameObject 9개 + 내부 3칸은 데이터)과 정합. `SGrid2D<Slot>` 전역 격자 + 각 Slot 안에 `SlotCell[3]` 데이터로.

**#3 기획서(임소영 v1.3) 보강**: 3×3 9슬롯 / 27칸 / 슬롯 위치 모든 스테이지 고정 — 동적 배치 아님. 데이터 드리븐 불필요, 씬에 프리팹으로 직접 배치 가능.

### 1-2. 빈 슬롯 배치 알고리즘 — 매치-3와 *정반대 목적*

#3 기획서(임소영 v1.3) 9-2 우선순위 배치:

1. 동일 기물 2개인 기물 (3-Sort 직전 유도)
2. 동일 기물 3개인 기물 (보드 인지 강화)
3. 대기 그룹 랜덤

**매치-3 `BoardSpawner.GetNonMatchingData`와 정반대 방향성**:
- 매치-3: *초기 배치 시 3매치 회피* (게임 시작 직후 자동 매치 방지)
- 「총알소녀」: *빈 슬롯에 매치 가능성 유도* (3-Sort 완성 동선 제공)

→ 매치-3 코드 재활용 불가. 새로 작성 영역. 단 *카운트 후 후보 필터링 → 랜덤 선택* 패턴은 비슷하므로 코드 골격 참조 가능.

### 1-3. 대기 그룹 패턴 — 매치-3에 없던 메커닉

「총알소녀」는 *유한 풀(대기 그룹)에서 꺼내 슬롯에 배치*하는 흐름. 매치-3 `BoardSpawner`의 *무한 랜덤 데이터*와 다름.

| | 매치-3 | 「총알소녀」 |
|---|---|---|
| 기물 소스 | `BlockDataSO[]`에서 무한 랜덤 | `WaitingGroup`에서 유한 풀로 꺼냄 |
| 풀 고갈 시 | 해당 없음 (무한) | 모든 슬롯 비었을 때 재생성 |
| 사용자 노출 | 풀 개념 없음 | 풀 비공개 (시스템 DB 내부) |

→ 새 클래스 `WaitingGroup.cs` 필요. *List 또는 Queue*로 구현, *기물 타입별 카운트*도 제공해야 우선순위 알고리즘이 *대기 그룹에 해당 기물이 있는지* 확인 가능.

### 2. 인터랙션 방식 — 드래그 vs 탭-탭

**의문점**: 우리 결정은 *드래그로 기물을 빈 셀로 이동*인데, 기획안 2.4.1은 *기물 선택 → 대상 셀 선택* (탭-탭 방식)으로 적혀 있음. 멀티터치 두 번째 무시 같은 예외 처리도 *탭-탭 가정*.

→ 기획팀에 확인 필요. 드래그면 핸들 개념이 *드래그 중인 기물 참조*로, 탭-탭이면 *선택된 기물 임시 저장*으로 다름.

**#3 기획서(임소영 v1.3) 7-1B 확인**: *"플레이어가 드래그 중 올바르지 않은 위치에 기물을 이동할 경우 원래 기물이 있던 위치로 배치됩니다"* — **드래그 방식 확정**으로 보임. 묶음 B는 드래그 가정으로 진행 가능.

### 3. 매치-3 코드 폐기 비율이 큰 이유

매치-3와 「총알소녀」는 **인터랙션·판정·결과 처리가 다 다른 게임**임:

- 인터랙션: 매치-3는 *인접 두 블록 스왑*, 「총알소녀」는 *기물을 빈 셀로 이동*
- 판정: 매치-3는 *가로·세로 라인 3+개*, 「총알소녀」는 *한 슬롯 안 3개 동일*
- 결과: 매치-3는 *제거→낙하→리필→연쇄*, 「총알소녀」는 *기물 비우기 + 포탑 소환 요청*

→ 알고리즘·연쇄 처리·이동 시스템이 거의 다 다르므로 폐기 비율이 큰 것은 자연스러움. **재활용 가치는 *코드 자체*가 아니라 *구조·패턴·인터페이스 분리 철학*에 있음.**
