> **대상**: 전 팀원 (기획 / 개발 / 그래픽 등 직군 무관)

## 0. 이 문서에 대하여

이 문서는 **모든 직군이 함께 읽는 공용 협업 규칙**이다. 코드나 기술 세부사항은 다루지 않는다. 개발 환경·코어 시스템 관련 내용은 개발자 전용 문서를 따로 둔다.

이번 프로젝트의 3대 원칙은 다음과 같다.

1. **기업 미션 충족** — 협약사가 요구한 미션이 최우선 판단 기준이다.
2. **기획팀과의 긴밀한 협업** — 기획·개발이 같은 정보를 공유한다.
3. **빠른 개발** — 완벽함보다 동작하는 결과물을, 일정 안에서 만든다.

> ⚠ 컨셉 기획이 확정되었다(컨셉 기획서 v0.1). 게임은 「총알소녀」 — 3-Sort로 포탑을 소환해 웨이브로 몰려오는 몬스터를 막는 캐주얼 모바일 디펜스다. 프로젝트명은 가제이며 정식 명칭은 추후 확정한다. 게임 화면 구성(분포형/밀집형)과 포탑 대기열 시스템 등 일부 세부는 기획에서 확정 중이다.

### 기업 미션 정리

> 협약사(유닉온)가 제시한 미션의 **핵심 요구사항**이다. 모든 작업 우선순위 판단은 이 내용을 기준으로 한다.

**미션**: 위에서 내려오는 적을 막는 **디펜스**와, 슬롯에 같은 아이템을 모으는 **3정렬(3-sort)** 퍼즐을 결합한 캐주얼 모바일 게임 제작.

**필수 유저 체험 (3가지)**

- 몰려오는 몬스터를 보며 느끼는 압박감 (스릴)
- 콤보로 정렬을 완성해 몬스터를 한 번에 쓸어버리는 쾌감
- 플레이마다 다른 성장 방식을 선택하는 데서 오는 전략적 재미와 반복 플레이성

**필수 기능 ((필) 표시는 핵심 구현 대상)**

- 튜토리얼/온보딩 — 글자 사용 최소화, 가장 낮은 단계부터 점진적 난이도 상승
- 스테이지 선택/진행 — 로비에서 스테이지 선택 후 진입
- 옵션 — 로비/인게임 별도 (사운드 조절, 인게임 일시정지 및 선택지 목록)
- 시간 제한 / 목표 제시 — UI로 달성 목표 표시
- (필) 인게임 경험치 & 보상 — 적 처치 시 경험치, 일정 수치 도달 시 보상
- (필) 몬스터 생성 & 이동 시스템
- (필) 공격 & 스킬 시스템 — 3정렬 성공 시 발생하는 공격, 선택지로 버프되는 스킬
- (필) 선택지 성장 — 경험치가 차면 랜덤 선택지 등장, 레벨·이전 선택에 따라 풀 변화
- (필) 3-sort 시스템 — 한 슬롯에 같은 아이템을 드래그해 모으면 클리어
- (필) 게임 클리어 / 오버 — 목표 종료·실패 처리
- 스테이지 정산 페이지 — 종료 시 획득 아이템·선택 내역 확인 (스테이지 종료 → 정산 → 로비)
- (필) 인게임 텍스트 시트 관리 — 한/영 시트 기반 텍스트 관리 (현지화)

### 게임 컨셉 요약 (컨셉 기획서 v0.1 기준)

> 전 팀원이 공유하는 게임의 한 장 요약이다. 상세는 기획팀의 컨셉 기획서를 따른다.

**한 줄 컨셉**: 3-Sort로 포탑을 소환해 몬스터를 막고, 강화 선택으로 다음 정렬 전략이 달라지는 모바일 디펜스.

**코어 루프**: 압박 → 판단 → 정렬 → 공격 → 해소 → 성장 → 다음 압박. 게임 시작 → 몬스터가 슬롯 공격 → 3-Sort 정렬 → 포탑 소환 → 몬스터 처치 → 경험치 획득 → 강화(특전) 선택 → 다음 웨이브.

**핵심 구성 요소**

| 요소 | 역할 |
|---|---|
| 기물 | 플레이어가 정렬하는 대상이자 포탑 소환 재료 |
| 슬롯 | 기물을 담는 제한 공간 + HP를 가진 방어 대상 (모두 파괴 시 패배) |
| 포탑 | 같은 기물 3개 정렬 시 소환되는 공격 수단 (권총/샷건/로켓/레이저/스나이퍼/기관총/둔화 등) |
| 몬스터 | 위에서 내려오는 적 (기본/고속/탱커/군집/보스 등 유형별 특성) |
| 강화(특전) | 레벨업 시 선택하는 성장 요소, 다음 정렬 전략을 바꿈 |
| 콤보 / 필살기 | 연속 정렬 보상(콤보) / 전체 기물 정렬 시 보상(필살기) |

**기본 진행 규칙**: 한 스테이지 = 10웨이브, 웨이브당 약 40초 정해진 배치로 몬스터 등장, 웨이브 종료 후 정비 시간에 특전 선택. 같은 기물 3개가 한 슬롯에 모이면 정렬 처리 → 포탑 소환.

**승패 조건**: 주어진 웨이브의 적을 모두 처치하면 승리, 보유한 슬롯이 모두 파괴되면 패배.

### 프로젝트 목표

- 필수 유저 체험 3가지(압박감 / 콤보 쾌감 / 성장 선택)가 분명히 느껴지는 플레이 가능한 결과물 제작
- 필수 기능 중 **(필) 표시 항목을 최우선**으로 구현
- "3-Sort 성공 = 포탑 소환 = 공격"이 끊김 없이 연결되는 핵심 루프 완성
- 데이터 드리븐 구조(Excel/JSON)로 기획-개발 협업 효율 확보

## 3. 그라운드 룰

### 3.1 작업 영역 존중

- 각자 작업 중인 영역을 침범하지 않는다.
- 타인의 작업 영역은 무통보 수정 금지. 수정이 필요하면 담당자에게 먼저 알린다.
- 공동으로 쓸 가능성이 높은 파일·에셋을 바꾸려면 사전에 공유한다.
- 작업이 끝난 결과물은 재사용 가능한 단위(프리팹 등)로 정리해 공유한다.

### 3.2 막힘 / 변경 공유

- 장시간 막히면 혼자 끌지 말고 **즉시 공유**한다. 빠른 개발이 목표이므로 막힘을 빨리 드러내는 것이 팀 전체에 이득이다.
- 일정에 영향이 갈 문제는 **미리** 알린다. 사후 통보는 지양한다.
- 매일 진행 상황을 짧게라도 공유한다.

### 3.3 태도

- 작업 시간에는 집중하고, 각자 컨디션을 관리한다.
- 의사결정은 기록으로 남긴다. "회의에서 정했는데 기억이 안 난다"를 방지한다.

## 4. 기획-개발 협업 규칙

### 4.1 기능 단위 합의

- 작업은 **세부 기능 단위**로 쪼개어 문서/보드에 올린다.
- 새 기능은 기획이 요구사항을 정리 → 개발이 구현 범위·난이도를 회신 → 합의 후 착수. 구두 합의만으로 큰 기능을 시작하지 않는다.
- 기획 변경이 발생하면 변경된 내용을 문서에 반영하고 개발에 공유한다. **문서에 없는 변경은 합의되지 않은 것으로 간주**한다.

### 4.2 우선순위 판단 기준

- 기능 충돌·일정 압박 시 판단 기준은 다음 순서를 따른다.
  1. 기업 미션 필수 요구사항인가
  2. 없으면 결과물이 성립하지 않는가
  3. 일정 안에 안정적으로 끝낼 수 있는가
- 위 기준으로도 애매하면 팀장이 조율한다.

### 4.3 빠른 개발을 위한 약속

- **동작하는 최소 버전 먼저**, 폴리싱은 나중에. 첫 시도에서 완벽을 노리지 않는다.
- 어떤 기능을 개발하다 막히면 **확실히 완성하거나, 안 되면 빠르게 포기**하고 대안을 찾는다. 어중간한 미완성을 끌고 가지 않는다.
- 특정 인원에게 작업이 몰리면 넘길 수 있는 것은 분배한다.

### 4.4 피드백

- 피드백은 사람이 아니라 결과물·기능을 대상으로 한다.
- 테스트 후 발견한 문제는 재현 방법과 함께 공유한다.

## 5. 기업 커뮤니케이션 가이드

> 협약 기업(유닉온) 및 담당 강사와의 소통에 적용한다. 팀 내부 소통에도 기본 태도로 권장한다. 대외 커뮤니케이션은 팀 전체의 인상을 좌우하므로 전원이 숙지한다.

### 5.1 소통 가이드

- **상호 존중**: 직급·나이와 무관하게 항상 경어를 쓰고 서로를 존중한다.
- **업무 시간 준수**: 원활한 협업을 위해 평일 09:00~18:00 사이의 소통을 권장한다. (긴급 상황 제외)
- **신속한 답변**: 확인이 늦어질 경우 사유를 먼저 전달하고, 늦게 확인했을 때는 예의를 갖춰 양해를 구한다.
- **요약 중심**: 내용이 길어지면 메시지 상단에 핵심 요점부터 정리해 공유한다.
- **사전 확인 필수**: 중복 질문을 막기 위해 이전 대화를 먼저 검색하고, 담당 강사 확인을 거친 뒤 최종적으로 기업 측에 메시지를 전달한다.

> ⚠ **기업 측 문의 절차**: 기업에 직접 보내는 메시지는 **반드시 담당 강사 확인 후** 전달한다. <br>
> 개인이 임의로 기업 측에 연락하지 않는다. 문의가 필요하면 팀 내부 → 강사 확인 → 기업 순서를 지킨다.

### 5.2 자료 공유 및 관리

- **파일명 규칙**: 누가 봐도 한눈에 알 수 있는 명확한 파일명을 쓴다. 예: `[7팀]_미션수행서_260515.docx`
- **보안 주의**: 자료 공유 전, 보안상 문제가 될 정보나 개인정보가 포함되어 있지 않은지 반드시 검토한다.

## 6. Git 워크플로우

> 코드뿐 아니라 문서·기획 자료도 같은 저장소에서 버전 관리할 수 있다. 비개발 직군도 최소한의 Git 흐름은 따른다.

### 6.1 브랜치 전략

| 브랜치 | 용도 |
|---|---|
| `main` | 최종 빌드·배포용. 직접 푸시 금지 |
| `develop` | 개발 통합용. 모든 PR은 여기로 |
| `feat/기능명_작성자` | 개인 작업 브랜치 |

- 네이밍 규칙: `접두사/기능_작성자` (예: `feat/title-ui_LSG`)
- 작업 순서: `develop`에서 브랜치 생성 → 작업 → `develop`으로 PR → Merge 후 브랜치 삭제
- 안 쓰는 오래된 브랜치는 삭제해 혼동을 막는다.

### 6.2 커밋 컨벤션

커밋 전 필수 체크: **에러 0개, 동작 확인 완료**.

커밋 메시지 prefix:

| prefix | 용도 |
|---|---|
| `feat:` | 새 기능 추가 |
| `fix:` | 버그 수정 |
| `docs:` | 문서 수정 |
| `refactor:` | 코드 리팩토링 |
| `chore:` | 빌드·설정 변경 |

- 작은 변경은 제목만으로 설명하고 본문은 생략 가능.
- 참고: [Udacity Git Commit Style Guide](https://udacity.github.io/git-styleguide/)

### 6.3 PR 규칙

- PR 병합 전 동작·에러를 확인한다.
- `main` / `develop` 양쪽에 GitHub 브랜치 보호 규칙이 적용되어 있다. 직접 푸시는 막혀 있다.
- 병합 담당자: 이성규 (플밍 팀장). 모든 머지는 팀장을 거친다.
- **팀장 부재 시 부팀장(안정연)이 머지를 대행**한다. 안정연은 Maintain 권한 + bypass 권한을 가진다.
- **bypass 운영 약속**: 팀장만 평상시 bypass 사용 가능. 부팀장은 *팀장 부재·외부 사유로 정상 흐름이 막힐 때만* bypass를 사용한다. 본인이 올린 PR을 본인이 bypass로 머지하지 않는다.
- 머지 완료 시 소통 채널에 통보한다.

### 6.4 복구

- 파일이 깨지면 Git에서 이전 버전으로 되돌린다.
- Unity 씬·에셋을 되돌릴 때는 **메타파일(.meta)까지 함께** 복구한다. (매우 중요 — 메타파일 누락 시 참조가 깨진다.)

## 7. 에셋 관리

### 7.1 외부 / 유료 에셋

- **GitHub 업로드 금지** (라이선스 이슈).
- 외부 에셋은 별도 폴더에 모아 `.gitignore` 처리하고, 공유는 별도 드라이브로 한다.
- 공유 드라이브 경로: (킥오프 확정)

### 7.2 외부 플러그인 / 패키지

- 사용 전 라이선스 확인 + 팀장 승인 필수.
- 새 플러그인·패키지를 추가하면 반드시 소통 채널에 통보한다. (신규 팀원 셋업이나 빌드에 영향을 주기 때문.)
- **미션 지정 필수 에셋**: DoTween(연출), UGUI(UI). 이 둘은 기본 채택이며 별도 승인 불필요.
- 외부 리소스를 사용하면 **라이선스 문서와 출처 링크를 반드시 보관**한다. (유닉온 산출물 #4 요건.)

### 7.3 네이밍

- 폴더 트리로 대분류를 나눈다.
- 파일·프리팹 이름은 `속성_이름_특이사항` 형태로 **2가지 이상 요소**를 포함한다. (예: `UI_Title_Main`, `Char_Player_Default`)
